# 事件评论采集 Agent（B 站真实抓取）

给一个事件，自动检索相关视频、按热度定帖、抓取评论区、清洗采样、出立场与议题分析。
**抓取部分全部是真实网络请求**，不是模拟数据。

```powershell
# 完整跑：检索 → 定帖 → 抓评论 → 分析 → 报告
py pipelines/comment_harvest/agent.py --event "武汉万圣节网约车"

# 只重跑分析：复用已抓到的原始评论，1 秒出结果
py pipelines/comment_harvest/agent.py --event "武汉万圣节网约车" --reuse var/comment_harvest/<run_dir>
```

产物写在 `var/comment_harvest/<事件>_<时间戳>/`：`report.md`、`comments.json`（采样 100 条）、
`comments_raw.json`（全量）、`candidates.json`、`posts.json`、`analysis.json`、`cost.json`、
`llm_prompts/`（喂给模型的原始提示词）。

## 1. 为什么这样拆

### 1.1 先把「找」和「读」分开

找热帖是**排序问题**，读评论是**归纳问题**，两者的输入规模差两个数量级。
把 40 个候选视频的全文塞进一个上下文再让模型自己找，token 会爆；而先做一次规则打分，
模型只需要看 4 个标题——这一步省掉的钱比任何提示词优化都多。

### 1.2 热度分不能靠模型直觉

```
hotness = 0.35·log10(1+播放)/7
        + 0.30·log10(1+评论)/5
        + 0.20·exp(-年龄/72h)
        + 0.15·log10(1+点赞)/6
```

四项各自先归一化到 0~1 再加权，因为播放量和评论量不在一个量纲上。
本次事件里，播放量最高的视频（78 万）并不是评论最多的（6,267 条），排序后两者都被选中——
如果只按播放排，会漏掉真正在吵架的那条。

### 1.3 前 100 条热评是最差的样本

热评奖励情绪和抖机灵，直接取会得到一张夸张的脸。所以按三通道分层抽：

| 通道 | 本次占比 | 作用 |
| --- | ---: | --- |
| 热评（按赞） | 44% | 主流可见意见 |
| 最新（按时间） | 28% | 事件演进、最新反转 |
| 时间轴随机 | 28% | 捞回沉底的长尾与反驳 |

抓取时按 1.4 倍放大（目标 100 → 实抓 1,904 条），对冲清洗损耗。

### 1.4 立场比情感更贴这批语料

第一版用「正面/负面/中性」词表，结果 87% 判成中性——因为这条线的主体不是骂街，
是**地域争论**：「武汉确实没有网上传的那样」和「武汉是这样的」情绪强度相近，
只有立场相反。所以主维度改成 6 类立场，情感降为辅助列。

## 2. 真实抓取踩到的坑（本次实际遇到）

这部分才是「爬网页」的真身。同样的代码在纸上跑通和在线上跑通，差别全在这里。

### 2.1 老评论接口已经被降级

`/x/v2/reply?pn=1&ps=20` 第一次调还能返回 20 条，跑几次之后：

```text
pn=1 rows=3 count=1467      ← 只给 3 条
pn=2 rows=0 count=0         ← 后面全是空
```

第一轮就是这样只抓到 75 条评论（目标 100）。这不是代码 bug，是接口层面的软限流：
分页翻深了就不给数据，且返回 `code=0`（成功），不报错，静默降级。

### 2.2 必须走 wbi 签名的游标分页

正确入口是 `/x/v2/reply/wbi/main`，需要三样东西：

1. 先 `GET /x/web-interface/nav` 拿 `wbi_img.img_url` 与 `sub_url`；
2. 用固定的 64 位置换表混合出 `mixin_key`；
3. 参数按 key 排序后 `urlencode` + `mixin_key` 做 MD5，得到 `w_rid`，连同 `wts` 一起带上。

```python
origin = img_basename + sub_basename
mixin_key = "".join(origin[i] for i in _MIXIN)[:32]
query = urlencode(sorted_params)
w_rid = md5(query + mixin_key).hexdigest()
```

签名只解决「能不能调」，不解决「怎么翻页」。

### 2.3 翻页游标藏了两层

响应里的游标不在顶层：

```json
{ "data": { "cursor": { "is_end": false,
                        "pagination_reply": { "next_offset": "CAEiAggC" } } } }
```

第一版读 `data.pagination_reply`，永远是 `null`，于是每轮都以为到底了，只拿到 20 条。
正确路径是 `data.cursor.pagination_reply.next_offset`，且它非空不代表没到底，要与 `is_end` 一起判。
改对之后，单条视频稳定翻到 7 页 138 条，四条视频合计 1,904 条。

### 2.4 深翻必超时

第 8 页开始出现 `TimeoutError: read operation timed out`。处理方式是：

- 每次请求间隔 1.2 秒（`--qps`）；
- 超时/`-412`/`-799` 退避重试最多 4 次；
- 单页失败不抛整体，能拿多少算多少。

本次 255 次请求、568 秒跑完，其中相当一部分时间在等限速——**这笔账花的是时间，不是钱**。

### 2.5 微博、知乎这条路是堵的

同时探了另外两个源：

| 源 | 结果 |
| --- | --- |
| B 站搜索 | 能用，无需登录 |
| 微博 `m.weibo.cn` | 返回非 JSON（需要 Cookie/桌面端签名） |
| 知乎搜索 API | 403 |
| 百度 | 可访问，但结果页无平台外链（JS 渲染 + 反爬） |

所以本次数据全部来自 B 站。这不是偷懒，是公开接口可达性的真实边界；
要接微博/知乎得单独做 Cookie 池或浏览器渲染，成本另算。

### 结果里最值得说的一个数

| 立场 | 条数占比 | 赞数占比 |
| --- | ---: | ---: |
| 批评城市形象 | 16.0% | **33.7%** |
| 反驳地域黑 | 13.0% | 14.6% |
| 玩梗嘲讽 | 9.0% | 7.3% |

也就是说：评论区的主战场已经从"这群人该不该被罚"漂移到"武汉这个城市怎么样"，
真正在讨论事件本身的声量极小。这个结论只靠"情感正负面"是看不出来的。

## 5. 已知局限

- **规则打标不够用**：52% 落进"未归类"，情感 87% 中性。反讽和地域辩论必须靠模型，
  规则版本只用于无 Key 时跑通链路。
- **单一平台**：只有 B 站，缺微博/抖音/小红书。结论不能外推成"全网舆论"。
- **样本非随机**：分层抽样，比例只代表样本；且只抓了一次，没有时间序列。
- **楼中楼覆盖不全**：只对 `rcount>=5` 的热评补采，深层回复会漏。
- **视频相关性靠关键词**：标题/简介命中"网约车/万圣/武汉/司机"，会有噪声（本次 42 个候选里
  明显无关的被热度排序自然挤掉了，但没有硬过滤）。
