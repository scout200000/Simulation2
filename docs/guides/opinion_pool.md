# 初始舆论池：生成式与采集式

第一轮评论（初始舆论池）现在有两种来源，由设置页的「初始舆论池」一栏选择，
决定后写入该批次 `web_control.json` 的 `opinion_pool` 字段，重跑与回滚口径一致。

| 来源 | 做法 | 适用 |
| --- | --- | --- |
| `generate`（默认） | 大模型按事件角度 + 人物类型合成 | 需要精确控制情绪配额、派系覆盖 |
| `harvest` | 从 B 站公开评论区抓真实评论，采集时完成标注 | 需要真实舆论形态、做对照实验 |

```powershell
# 改默认值（也可不改，直接在设置页选）
notepad configs/opinion_pool.json

# 不启动服务，单独试跑采集式
py backend/scripts/try_harvest_pool.py --count 40 --videos 3
```

## 1. 配置从哪里来

优先级：**本次请求 > 会话已存配置 > `configs/opinion_pool.json` > 内置默认值**。

```json
{
  "source": "harvest",
  "generate": { "comment_count": 60 },
  "harvest": {
    "comment_count": 40,
    "videos": 3,
    "hot_pages": 2,
    "new_pages": 1,
    "expand_ratio": 1.5,
    "qps": 1.2
  }
}
```

前端把设置拼成 `opinion_pool_config` 随 `POST /api/sessions` 提交，后端在
`create_web_experiment` 里用 `resolve_config` 归一化后存进 control：

```text
设置页 → console.js → POST /api/sessions {opinion_pool_config}
      → session_service.create_web_experiment(opinion_pool_config=...)
      → control["opinion_pool"] = 归一化后的配置
      → start 时 build_initial_comment_pool(event_input, control["opinion_pool"])
```

## 2. 采集式做了什么

```text
事件正文
  ├─ 模型规划检索式（失败退回启发式：去时间词后取地名前缀）
  ├─ B 站搜索 ×4 → 视频去重
  ├─ 关键词硬门槛：一个关键词都不中说明跑偏了，直接失败
  ├─ 模型判「是不是同一件事」+ 地名锚点复核
  ├─ 一轮没找到就放宽重试（县级地名 → 市级地名，保留核心动作）
  ├─ 评论抓取：热门 2 页 + 最新 1 页（wbi 签名 + 游标分页）
  ├─ 清洗：去重、去广告、去纯表情、长度下限 8 字
  ├─ 派系判定：按文本特征给每条评论定派系（不靠模型印象）
  ├─ 配额采样：每派保底 + 单派上限，取 1.5 倍冗余（40 条 → 60 条）
  ├─ 标注：一次请求，输出 5 元组
  └─ 组装：剔除 relevant=0 → 二次配额采样到 N 条，产出与生成式同构的 comment_pool.json
```

标注输出是位置对齐的整数元组，不回传评论 id、不写中文枚举：

```json
{"clusters": ["城市形象质疑", "处罚力度争议"],
 "tags": [[0, 2, 3, 1, 1], [1, 2, 3, 1, 1]]}
```

五位依次是 `议题 / 情绪 / 立场 / 信息取向 / 相关性`。派系不交给模型——
它对「表达方式」的判定很不稳（实测 40 条里 34 条判成同一派），改由程序按文本特征判定。
议题名由模型在本批语料上归纳，再回填成 `angle_plan`——角度是**从数据里长出来的**，
不是凭空编的。角度计划在写入前会过一遍生成式的 `validate_event_angle_plan`，
保证 `angle_id / angle_name / focus / evidence_text` 四个字段与下游完全一致。

## 2.5 相关性怎么保证

取数最容易出的不是成本问题，是**抓错事件还看不出来**。一次真实事故：

```
事件：8月29日中午，河北省保定市高阳县一商场门口发生两名女子冲突……
检索式：['中午', '中午 司机', '中午 事件', '中午 处理']     ← 头两个字被日期剥离吃掉了
结果：抓到「三鹿奶粉事件」（213 万播放）和「如何带饭」，产出了 6 个奶粉议题
```

三个缺陷叠加，且全程没有任何报错：

| 缺陷 | 表现 |
| --- | --- |
| 检索式退化 | `8月29日中午` 剥掉日期剩 `中午`，两字直接当查询 |
| 没有硬门槛 | 关键词一个都没命中时 `matched or 全部`，静默接受全部结果 |
| 排序只看热度 | 213 万播放的无关视频压过真正的相关视频 |

现在有四道闸：

1. **检索式交给模型**：`{"queries": [...], "keywords": [...]}`，并强制关键词必须原样出现在事件正文里；
2. **关键词硬门槛**：零命中直接抛错，不允许「全部兜底」；
3. **模型判同事件**：把候选标题给模型，只留确实在讲同一件事的；再叠一道**地名锚点**，
   挡住「同地区不同事件」（如高阳县的螺蛳粉凳子事件）；
4. **放宽重试**：第一轮没找到就把县级地名换成市级地名再来一次。

锚点匹配容忍地名层级差：事件写「高阳县」，标题只写「保定」时也算命中。

代价是每次采集多 2 次小模型调用（约 600 输入 / 200 输出，¥0.0002）。这笔钱买的是
「抓不到就失败，而不是抓错还自洽」。

## 3. 三个降本点

| 手段 | 效果 |
| --- | --- |
| **减量**：默认 40 条而非 60 条 | 标注输出直接少 1/3 |
| **压缩标注**：一次请求 + 整数元组 | 每条输出从 ~33 token 降到 ~14 token |
| **相关性过滤**：多标一位 `relevant` | 跑题段子被剔除后，40 条就够用，不必多抓 |

## 3.5 派系怎么判、怎么均衡

派系描述的是「表达方式」，用可解释的文本特征判定：论证词 + 长文 → 观点输出；
感叹号 + 情绪词 → 情绪激进；指向群体的对立表述 → 矛盾激化；玩梗反问 → 吃瓜；
都不明显 → 表态判断（残差类）。同一条评论每次运行都得到同一个派系。

配额规则是「保底 + 上限」，且只影响**选谁进池**，不改标签：

```
每派至少 5 条（目标 < 25 条时按比例下调）
单派不超过目标的 40%
余量按各派可得数量比例分配
```

实测效果：同一批语料，「表态判断派」从 34/40（85%）降到 16/40（40%），五个派系全部出现。
代价是采样有轻微偏置——这是**明示的**采样口径，不是标签造假：
`faction_coverage.counts / quota / available / short` 全部落盘可查。

## 4. 实测对比（武汉万圣节网约车事件）

| | 生成式 | 采集式 |
| --- | ---: | ---: |
| 产出条数 | 60 | 40 |
| LLM 请求 | 7–8 | 1 |
| 输入 / 输出 token | 15,286 / 8,320 | 1,631 / 558 |
| 合计 token | 23,606 | **2,189** |
| 模型费 | ¥0.043 | **¥0.0041**（提示词命中缓存时 ¥0.0026） |
| 耗时 | 50–64 秒 | 23–34 秒（其中抓取 9 次请求） |
| 每 100 条 | ¥0.072 | **¥0.010** |

生成式的 77% 花在输出端（每条要写全文 + 10 个字段）；采集式的输出只有 6 个整数，
大头变成了一次性的提示词。

## 5. 限制

- **只有 B 站**。微博返回非 JSON、知乎 403、抖音需要签名，公开接口可达性决定边界。
- **不能用于历史校准**。`initial_opinion.json` 要求情绪配额与人工统计精确一致，
  采集拿到的是真实分布，对不上；`initial_opinion` 非空时会直接报错，请改用生成式。
- **派系配额受语料限制**。按「每派保底 5 条 + 单派不超过 40%」采样；
  但原始语料里某派本来就不足 5 条时（例如此次「情绪激进派」只有 4 条），
  池里就只能是 4 条，并如实记在 `faction_coverage.short`，不会为了凑配额改标签。
- **单次快照**。只抓一次，没有时间序列；同一事件重复跑会拿到不同样本。

## 7. 排障

### 增量运行报「第 N 个事件角度字段不完整」

```
ValueError: 第 1 个事件角度字段不完整。
  at incremental_generator._prepare_incremental_generation_inputs
     -> angle_planner.validate_event_angle_plan(pool["angle_plan"], event_context)
```

**原因**：2026/11/09 之前的采集式池子只写了 `angle_focus`（评论字段名），
而角度计划要求的是 `focus`；增量生成阶段会用生成式的校验器读这份计划，于是报字段缺失。

**处理**（二选一）：

```powershell
# A. 原地修复：用评论里现成的角度名重建计划，不重爬、不花模型额度
py backend/scripts/repair_harvest_pool.py --pool var/experiments/<批次>/comment_pool.json --in-place

# B. 重新生成：删掉池子后重启该批次（会重新抓取，40 条约 30-60 秒、0.005 元）
Remove-Item var/experiments/<批次>/comment_pool.json
```

修复脚本会同时做两件事：重建 `angle_plan`、把评论的 `angle_id` 按角度名重新对齐，
最后用 `validate_event_angle_plan` 和 `load_comment_pool` 双重校验。
