# LLM 调用说明

本文档记录仿真后端在运行回应方案对照、历史复现和采集式初始舆论池时调用
LLM 的业务环节。仿真侧所有 DeepSeek JSON 请求最终统一通过
`app/infrastructure/llm/llm_service.py` 中的 `call_deepseek_json()` 发出。

`pipelines/comment_harvest/llm.py` 和
`pipelines/persona_pipeline/deepseek_json_client.py` 是独立管线自带的客户端，
不经过上述服务；它们各自的运行说明见对应指南。

## 调用环节总览

| 环节 | LLM 主要功能 | 调用时机 |
| --- | --- | --- |
| 事件角度规划 | 根据事件正文生成可复用的事件讨论角度 | 生成式初始评论池，每个批次一次 |
| 初始评论池生成 | 根据事件、角度和评论画像生成结构化初始评论 | 生成式初始评论池，每个批次一次 |
| 采集式舆论池 | 规划检索式、判断候选是否同一事件、给采集评论打标 | 采集式初始舆论池，创建/启动会话时 |
| 增量评论生成 | 根据当前事件状态、官方声明和上一轮舆情生成本轮新评论 | 进场前共享路径每轮一次，分叉后每个场景每轮一次 |
| Agent 状态裁决 | 只输出内部情绪与官方态度（回应方案路径） | 每个场景、每个 Agent、每轮一次 |
| Agent 完整决策 | 输出情绪、官方态度、发言意愿、派系和原创表达（历史路径） | 历史复现每个 Agent、每轮一次 |
| 原创表达 | 仅在本地门控选择“原创”后生成公开表达 | 回应方案路径按需调用 |
| 全局趋势分析 | 判断舆情趋势是 `improving`、`stable` 或 `worsening` | 每个场景每轮一次 |

## 1. 初始评论池生成

调用链（生成式）：

```text
app/main/cli.py 或 session_service.create/start
→ app/comments/pool_generator.py
  → app/comments/angle_planner.py → llm_service.call_deepseek_json
  → app/comments/generation_service.py → llm_service.call_deepseek_json
```

`angle_planner.py` 先调用一次 LLM 生成事件专属角度计划。程序随后把初始
评论名额分配为角度任务，再由评论生成 LLM 针对指定角度选择人物类型和派系。

LLM 输入主要包括：

- 事件内容；
- 事件标签；
- 本批次程序分配的事件角度任务；
- 评论画像类型；
- 允许使用的评论派系、情绪、信息取向和立场。

LLM 输出包含任务编号、评论文本、人物画像编号、派系、情绪、信息取向和
立场等结构化字段。程序根据任务编号写入对应角度，不接受任务列表之外的编号。

生成式初始评论池默认 60 条，每批目标为 10 条，因此正常情况下至少发出
6 次请求。返回评论未通过字段校验、数量不足或派系覆盖不足时，系统会继续
调用 LLM 补齐。采集式舆论池不生成评论文本，改为抓取真实评论并调用模型
做检索式规划、同事件判断和标注，详见
[opinion_pool.md](../guides/opinion_pool.md)。

主要代码位置：

- `app/comments/angle_planner.py`：生成、校验并分配事件角度任务；
- `app/comments/pool_generator.py`：组织初始评论生成；
- `app/comments/opinion_pool.py`：生成式/采集式来源与配置归一化；
- `app/comments/generation_service.py`：执行评论批次生成、校验和重试；
- `app/infrastructure/llm/llm_service.py`：发送 DeepSeek 请求并解析 JSON。

## 2. 增量评论生成

第 1 轮直接使用初始评论池，不生成增量评论。从第 2 轮开始，回应方案对照
每个实际场景默认生成 8 条外生 LLM 增量评论，历史复现仍使用 20 条；事件
输入显式设置 `simulation_options.incremental_comment_count` 时以事件配置
为准。官方进场条件触发前只运行一条共享路径，触发后才复制状态并为各个
场景分别生成。

LLM 输入主要包括：

- 事件内容和当前事件状态；
- 当前官方声明及声明状态；
- 上一轮 Agent 实际表达的评论；
- 前一轮增量评论摘要；
- 本轮评论生成触发原因；
- 已有评论文本，用于减少重复；
- 本轮程序分配的活跃角度任务。

LLM 输出为本轮新增的结构化候选评论。批次会根据本轮目标数量自动拆分；
回应方案默认 8 条时通常只需一个首批请求，历史复现默认 20 条时通常为两个
首批请求。若评论被过滤或数量不足，系统会请求 LLM 继续补齐；重试结束后
仍不足时，再由本地评论兜底机制补足。

主要代码位置：

- `app/comments/incremental_generator.py`：构造增量评论上下文并组织生成；
- `app/comments/generation_service.py`：执行批次生成、结果校验和补齐重试；
- `app/infrastructure/llm/llm_service.py`：发送 DeepSeek 请求并解析 JSON。

## 3. Agent 决策

Agent 决策按两类实验分成两条提示词路径，不能混用。

### 3.1 回应方案对照：状态请求

每个场景中的每个 Agent 每轮调用一次“状态请求”：

- 输入：Persona、事件和当前状态、官方声明、该 Agent 的状态证据视图
  （最多 2 条邻居表达 + 5 条与 Persona 相关的公共评论）、上一轮状态；
- 输出：仅 `emotion` 与 `official_attitude` 两项，以及解释理由；
- 不包含发言意愿、动作、派系或评论文本。

发言意愿、原创/转发选择和公开表达由本地代码独立完成：

- 本地门控读取完整可见评论，决定沉默、原创或转发；
- 只有选择“原创”时才调用一次表达生成；
- 表达校验失败只重试表达，不回退修改内部状态。

### 3.2 历史复现：完整决策

历史路径保留完整决策请求：LLM 输出情绪、官方态度、发言意愿、派系和
原创表达；规则层先裁决状态，LLM 只解释既定状态并决定是否发言。历史路径
不选择评论池中的现成评论，发言时生成不超过 280 字的原创表达。

### 3.3 共同约束

- 状态证据按目标路由到事件情绪、官方态度和参与通道；
- 官方通告分句共享同一证据组，不能重复计数；
- 规则层推荐、证据记忆和逐条内部映射不进入 LLM 提示词；
- 同一次决策不保存 `llm_requested_speech`，行为只认本地门控结果。

主要代码位置：

- `app/agents/decision_service.py`：单 Agent 决策与表达生成；
- `app/agents/batch_decision.py`：并发组织多个 Agent 的决策；
- `app/agents/decision_engine.py`：构造提示词、校验认知结果；
- `app/agents/strategy_behavior.py`：回应方案的行为门控；
- `app/agents/strategy_expression.py`：原创表达生成与校验；
- `app/infrastructure/llm/llm_service.py`：发送 DeepSeek 请求并解析 JSON。

## 4. 全局舆情趋势分析

每轮 Agent 决策完成后，系统分析初始评论与当前轮增量评论之间的变化。
官方进场前的趋势只分析一次，策略分叉后分别分析。

LLM 输入主要包括：

- 当前事件和官方声明状态；
- 初始评论；
- 当前轮增量评论（回应方案默认 8 条，历史复现默认 20 条）。

LLM 输出主要包括：

- 趋势方向；
- 趋势判断理由；
- 作为判断依据的评论编号。

第 1 轮没有增量评论，系统直接将其作为趋势基线并返回 `stable`，不会调用
LLM。从第 2 轮开始，每个场景每轮调用一次。

## 不调用 LLM 的环节

以下功能由本地代码完成：

- 官方声明进场阈值判断；
- 负面率、质疑率和接受率计算；
- Agent 可见评论抽样与状态证据筛选；
- 发言门控、原创/转发选择；
- 原创表达的证据边界校验与超长裁剪；
- Agent 状态和个人评论历史保存；
- 增量评论数量兜底；
- 策略比较、污染审计和结果文件保存；
- 事件知识图谱的规则抽取（策略运行后的自动入库不调用大模型）。

## 调用量与成本口径

当前默认配置为 30 个 Agent、最多 10 轮、每轮 8 条外生增量评论；完整
“全部策略”批次包含 1 个不回应基线和 4 个回应方案，共 5 个场景。一次
完整批次的最低调用量级为：

```text
事件角度 1 + 初始评论池约 6
+ 状态请求：共享首轮 30 + 4 个方案 × 9 轮 × 30 ≈ 1110（不含不回应场景）
+ 原创表达：按实际发言人数，通常每个场景每轮 5～20 次
+ 增量评论：每个场景每轮 1～2 批
+ 全局趋势：每个场景每轮 1 次
```

即 **1500 次以上逻辑请求**，实际次数取决于动态进场轮次、发言率、评论
补齐、JSON 校验失败和 HTTP 重试。历史复现每轮 30 次完整决策，增量评论
默认 20 条（事件可通过 `simulation_options.incremental_comment_count`
覆盖），请求量级相近。

单次调用默认 `temperature=0`、`timeout=120s`、最多重试 3 次；`llm_service`
按请求类型记录逻辑请求数、HTTP 尝试数、重试数、失败数、耗时以及
`prompt_tokens / completion_tokens / total_tokens / cached_tokens`。
实验结果中的 `performance.llm_requests` 就是这些统计的汇总，可作为实际
调用量和成本的唯一口径。
